## 一、认证凭据体系（审查 04/05 项，必须先修）

### 1.1 为什么必须改

改前签发端是"有界替身"：`POST /api/v1/auth/sessions {"stub":"ADMIN"}` 直接返回管理员
令牌，且 `lumin.auth.mode=session` 下该端点**仍然可用**（T37 当时正是这么取的令牌）。
等于生产环境留了一张无凭据的发卡机。

### 1.2 落地结构

| 层 | 文件 | 职责 |
|---|---|---|
| 契约 | `V20__password_credential.sql` | `password_credential`：登录名唯一、主体唯一、**只存 BCrypt 摘要**、失败计数与锁定时间落库 |
| 域策略 | `lumin-domain/.../identity/domain/PasswordPolicy.java` | 长度 10–72、四类字符≥3、不含登录名、弱口令清单（纯函数、无 IO、不调外部服务） |
| 应用 | `PasswordCredentialService` | 注册（建档+摘要+签发）、登录（锁定裁决+时间均衡）、改密（**撤销全部会话**+换发令牌） |
| 仓储 | `PasswordCredentialMapper` / `PasswordCredentialRow` | 失败计数/锁定/改密的原子更新 |
| 接入 | `PasswordAuthController` | `POST /api/v1/auth/registrations`、`/auth/password-sessions`、`/auth/password-changes` |
| 闸门 | `AuthSessionController` | 替身签发**仅 demo 模式**；非 demo → 403/A2001 |
| 过滤器 | `DemoAuthenticationFilter` | 免认证 POST 白名单收敛为 **7 条**：替身签发、登出、注册、口令登录、二次验证挑战（§2.2）、口令重置请求/确认（§6.2） |
| 依赖 | `spring-security-crypto` | BCrypt 用成熟库，不自研 |

令牌体系**没有第二套**：口令登录签发的仍是原来的不透明持有令牌（双 UUID、只存
SHA-256 摘要、12 小时、可撤销），解析/撤销语义不变。

### 1.3 安全口径（逐条可查）

| 要求 | 实现 |
|---|---|
| 口令不明文落库 | `BCryptPasswordEncoder(12)`；测试断言 `password_hash` 以 `$2a$` 开头且不含明文 |
| 失败锁定 | 连续 5 次 → 锁 15 分钟；**状态在库内**（多实例一致、重启不丢） |
| 防账号枚举 | 账号不存在也跑一次 BCrypt 比对；不存在/口令错/锁定一律 401/A0001 |
| 失败计数不被回滚 | `@Transactional(noRollbackFor = LuminBusinessException.class)`——否则 401 会把计数滚掉，暴力破解无限次 |
| 改密后旧令牌立即失效 | 改密同事务内 `revokeAllFor(subject)` 后换发新令牌（用户不掉线） |
| 禁止口令复用 | 新口令与旧摘要比对命中即 400/P1001 |
| 生产禁用演示身份 | `SecurityStartupValidator`：非 dev/local/test/ci 且 `auth.mode=demo` → **启动失败** |

### 1.4 如何验证

```powershell
cd lumin-backend
$env:LUMIN_TEST_DB_USERNAME='root'; $env:LUMIN_TEST_DB_PASSWORD='<本地测试库口令>'
mvn -B -pl lumin-bootstrap -am test
```

| 用例 | 覆盖 |
|---|---|
| `UGC044PasswordAuthIntegrationTest`(8) | 弱口令/含登录名拒绝、摘要存储、注册签发、5 次锁定（含 DB 断言）、改密旧令牌 401、禁用复用、demo 签发未误伤 |
| `UGC045SessionModeCredentialIntegrationTest`(3) | 生产模式下真实凭据可用、演示头被忽略、替身签发 403、未登录改密 401 |
| `T37SessionAuthIntegrationTest`(3) | 令牌解析/撤销/过期/注销联动语义（签发改为库内种入，因生产模式已关闭替身签发） |

## 二、二次验证（TOTP，审查 05 项"管理员额外要求"）

### 2.1 为什么必须改

口令单因子对特权账号不够：一个 ADMIN 口令泄露即等于全站管理权。改前既没有第二因子，
也没有"特权账号必须先登记第二因子"的闸门——`X-Lumin-Demo-Subject: ADMIN` 甚至能直接
拿到管理员身份（见 §1.1）。

### 2.2 落地结构

| 层 | 文件 | 职责 |
|---|---|---|
| 契约 | `V21__mfa_totp.sql` | `mfa_totp_credential`（种子密文、`PENDING/ACTIVE`、`last_used_step` 重放账本、主体唯一）；`mfa_recovery_code`（`code_hash CHAR(64)`、`used_at`、`(subject,code_hash)` 唯一） |
| 域 | `identity/domain/Totp.java`、`Base32.java` | RFC 6238 纯函数（HMAC-SHA1、6 位、30 秒步长、±1 步漂移、常量时间比较）；RFC 4648 Base32 编解码 |
| 应用 | `MfaTotpService` | 登记（种子只以 `FieldCipher` 密文落库，AAD `mfa.totp.secret`）→ 确认（校验一次码后 `ACTIVE` + 8 个一次性恢复码，只存 SHA-256）→ `isActive` / `verify`（验证码或恢复码） |
| 仓储 | `MfaTotpMapper`、`MfaRecoveryCodeMapper` | `insert/updatePendingSecret/activate/markStepUsed`；`findUnusedId/markUsed`（`markUsed` 以受影响行数做并发裁决） |
| 会话 | `AuthSessionService` | `issueChallenge`（5 分钟挑战令牌）、`issueEnrollmentRestricted`（30 分钟"仅可登记"受限会话）；`resolve` 拆为 `resolveRaw` + `resolve`（挑战令牌一律判非会话）+ `resolveChallenge` |
| 登录分流 | `PasswordCredentialService.LoginOutcome` | `SESSION / MFA_REQUIRED / MFA_ENROLLMENT_REQUIRED` 三态；特权判定取 `role_grant(APPROVED 且未过期)` 的 `ADMIN` |
| 接入 | `MfaController` | `POST /api/v1/auth/mfa/enrollments`、`/mfa/confirmations`、`/api/v1/auth/mfa-challenges` |
| 闸门 | `DemoAuthenticationFilter` | 豁免第 5 条 `/auth/mfa-challenges`；`MFA_ENROLL_ONLY` 令牌只放行 `/api/v1/auth/mfa/**` 与登出，越界 → 403/A2001 |

### 2.3 关于"自研 TOTP"的偏离登记（必须如实写）

本机 **Maven Central 不可达**（`repo.maven.apache.org` 解析失败），`~/.m2` 内无
`dev.samstevens.totp` / `otp-java` / `googleauth` 任何制品，因此无法引入成熟库。处理方式：

- **不发明算法**：只按 RFC 4226/6238 规定调用 JDK `Mac("HmacSHA1")` 拼装，动态截断、
  计数器编码、补零全部照文档；
- **用官方向量证明正确性**：RFC 4226 附录 D 计数器 0–9、RFC 6238 附录 B 六个时间点，
  见 `TotpTest`（6 用例）；
- **替换点单一**：`Totp.code` / `Totp.verify` 两个方法，调用方 `MfaTotpService` 无需改动。

这是对"禁止自造认证轮子"规则的**有理由偏离，且已登记**：一旦可引依赖应立即替换，
测试可原样保留作为回归基线。

### 2.4 安全口径（逐条可查）

| 要求 | 实现 |
|---|---|
| 种子不落明文 | `FieldCipher`（AES-256-GCM + AAD 绑定）；UGC046 断言库里取出的字节**不含**显式返回的 Base32 |
| 验证码重放 | `last_used_step` 单调前进；同一时间步的码第二次使用 → 401（UGC046 有反证） |
| 登记码不计入重放账本 | 确认时不记账（否则确认后 30 秒内首次登录会被重放保护误拒）；登记码一次换发会话即失效 |
| 恢复码单次 | 只存 SHA-256 摘要，`used_at` 置位后失效；复用 → 401 |
| 挑战令牌不能当会话 | `AuthSessionService.resolve` 对 `stub_name=MFA_CHALLENGE` 一律返回 null → `/me` 401 |
| 挑战令牌一次性 | 兑换成功即 `revoke`；重放 → 401 |
| 已启用不许重登记 | `ACTIVE` 再登记 → 409/B2001（防会话劫持者把种子换成自己的） |
| 特权账号未启用 | 只发 30 分钟受限令牌（业务端点 403），完成登记+确认后换正式会话 |
| 特权判定不信任替身名 | 只认 `role_grant`；demo 替身名在生产 `session` 模式下不可用（§1.2 闸门） |
| 确认失败不泄露细节 | 坏码 → 400/P1001，无 PENDING 凭据 → 409/B2001 |

### 2.5 如何验证

| 用例 | 覆盖 |
|---|---|
| `TotpTest`(6，`lumin-domain`) | RFC 4226 附录 D 全 10 行、RFC 6238 附录 B 6 个时间点、±1 步漂移、重放拒绝、格式非法、Base32 RFC 4648 向量与往返 |
| `UGC046MfaTotpIntegrationTest`(7) | 登记→确认（坏码 400 / PENDING 不变）→ 登录只回挑战令牌；挑战令牌 `/me` 401、一次性消费、同码重放 401；恢复码单次；ADMIN 未启用 → 受限令牌 `/me` 403 → 登记确认后恢复正常；普通读者不被误判特权；已 `ACTIVE` 重登记 409；登出后仍要求 MFA |

## 三、免认证入口的按 IP 配额（审查 19 项）

### 3.1 为什么必须改

账号级锁定（§1）只挡"盯住一个账号"的攻击；撞库的常见形态是**同一 IP 横扫一片账号**，
而登录 / 注册 / 二次验证挑战三个端口都没有凭据可锁——可以无限次尝试。改前 `RateLimitFilter`
按主体限流，且**默认关闭**、只覆盖写方法，对这四个免认证入口等于没有。

### 3.2 落地结构

| 层 | 文件 | 职责 |
|---|---|---|
| 契约 | `V22__auth_ip_throttle.sql` | `auth_ip_throttle(ip_hash, window_start, attempts)`，主键 `(ip_hash, window_start)` |
| 应用 | `AuthIpThrottleService` | 固定 1 分钟窗口；`acquire(ip, now)` 计数后裁决，超配额 → 429/A2003 |
| 仓储 | `AuthIpThrottleMapper` | `INSERT … ON DUPLICATE KEY UPDATE attempts = attempts + 1`（多实例原子累加）、`attempts`、`deleteBefore` |
| 接入 | `PasswordAuthController`、`MfaController` | 注册 / 口令登录 / 二次验证挑战三个入口在**任何凭据校验之前**先 `acquire` |

### 3.3 安全口径（逐条可查）

| 要求 | 实现 |
|---|---|
| 计数多副本一致 | 落库原子 UPSERT，不用内存窗口（`RateLimitFilter` 的单实例口径不再重复） |
| 换端点不能续命 | 三个入口共用一个桶（同一 IP 合计配额） |
| 先计数后校验 | `acquire` 在凭据校验前调用，不给"响应时间差探测配额"留口子 |
| 不存原始 IP | 只存 `SHA-256(ip + "|" + lumin.crypto.key)`，64 位十六进制；测试断言库里不含明文地址 |
| 被拒的那次不落库 | 超限抛异常 → 本方法事务回滚，库内停在"恰好达上限"，不会把计数推成天文数字 |
| 表不无限增长 | 新窗口首次计数时顺手 `DELETE` 2 小时前的窗口（每 IP 每分钟至多一次写放大） |
| 不信任 `X-Forwarded-For` | 取 `request.getRemoteAddr()`：该头可伪造，信任它等于把配额交给攻击者 |
| 默认配额 | 20 次/分钟（NAT/校园网出口共享配额可调），`lumin.auth.ip-limit.*` 可关可调 |

### 3.4 如何验证

| 用例 | 覆盖 |
|---|---|
| `UGC047IpLimitIntegrationTest`(5) | 超限 429/A2003（第 4 次即便口令正确也拦）、配额按 IP 独立、注册/登录/挑战共用一桶、挑战端点单用也被限、窗口按分钟对齐且地址只存摘要 |

## 五、MFA 运维解绑（审查 05 项遗留）

### 5.1 为什么必须改

`ACTIVE` 后禁止自行重登记（§2.4，防会话劫持者换种子）是刻意的，但**没有出口**：
手机丢失/换机即永久锁死在该账号外，只能改库。安全策略必须配一条受控、可审计的解绑通道。

### 5.2 落地结构

| 层 | 文件 | 职责 |
|---|---|---|
| 契约 | `V23__mfa_unbind_request.sql` | 状态机由 `PENDING/ACTIVE` 扩为 `PENDING/ACTIVE/REVOKED`；新表 `mfa_unbind_request`（`open_slot = IF(state='PENDING', subject, NULL)` 生成列 + 唯一索引 → **同主体同时只有一张待审申请**） |
| 应用 | `MfaUnbindService` | `request`（要求当前 `isActive`，理由必填≤500、重复提交 409/B2001）/ `listPending` / `decide`（角色 ∈ {OPERATOR, ADMIN}） |
| 仓储 | `MfaUnbindRequestMapper`、`MfaTotpMapper.revoke`、`MfaRecoveryCodeMapper.deleteAllFor` | 落申请、状态裁决（`PENDING` 守卫 + 乐观锁）、`ACTIVE→REVOKED` 同时清 `last_used_step`、清空恢复码 |
| 接入 | `MfaUnbindController` | `POST/GET /api/v1/mfa-unbind-requests`、`POST /{id}/decisions` |

### 5.3 安全口径（逐条可查）

| 要求 | 实现 |
|---|---|
| 不能自助解绑 | 申请人只能提交，批准必须 OPERATOR/ADMIN；无权限 → 403/A2001 |
| 解绑后可审计 | 批准写 `mfa.unbind.approved`（before/after 仅 `mfaState: ACTIVE→REVOKED`），WARN 级日志带工单号与操作员 |
| 解绑即断链 | 批准同事务：撤销种子 + 删除恢复码 + `revokeAllFor(subject)`（旧会话立即失效），不给"解绑同时保留会话"的窗口 |
| 不享受受限会话豁免 | 端点**刻意不放在** `/api/v1/auth/mfa/**` 前缀下——该前缀对 `MFA_ENROLL_ONLY` 受限令牌放行，运营端点不应享受这条豁免 |
| 重复申请不堆积 | 生成列唯一索引拦住第二张 `PENDING`；重复提交 409 而非默默排队 |
| 无效申请不产生副作用 | 驳回只改状态，种子与恢复码保持原样（UGC049 有反证：驳回后原 TOTP 码仍可登录） |

### 5.4 如何验证

`UGC049MfaUnbindIntegrationTest`(3)：批准 → 种子 `REVOKED`、恢复码清空、旧会话全撤销、旧 TOTP 码登不上；
驳回 → 第二因子仍然有效；READER 无权列/批（403/A2001）。

## 六、口令找回 / 重置（审查 04 项遗留，双通道）

### 6.1 为什么必须改

有口令体系却没有找回通道，现实后果是运营直接改库（绕过策略、无审计）。同时它是个高风险入口：
做错就等于"无凭据改密"，还能顺手绕过二次验证。

### 6.2 落地结构

| 层 | 文件 | 职责 |
|---|---|---|
| 契约 | `V24__password_reset.sql` | `password_credential.email`（唯一索引、多 NULL 不冲突）；`password_reset_ticket`（`channel ∈ EMAIL/CUSTOMER_SERVICE`、`state ∈ AWAITING_OPERATOR/PENDING/DELIVERY_FAILED/CONSUMED/REJECTED/EXPIRED`、`code_hash`、`expires_at`、`lock_version`） |
| 应用 | `PasswordResetService` | `request`（防枚举）/ `confirm`（比摘要 → 策略校验 → 改密 → 撤销全部会话）/ `listAwaiting` / `decide` |
| 通道 | `PasswordResetMailGateway` + `UnconfiguredPasswordResetMailGateway` | 端口 + **明确失败**兜底（日志不含码与收件人，抛 `MailDeliveryUnavailableException`）；`bootstrap/configuration/PasswordResetMailConfig` 以 `@ConditionalOnMissingBean` 注册 |
| 接入 | `PasswordResetController`、`PasswordResetTicketController` | `POST /api/v1/auth/password-resets`、`/auth/password-reset-confirmations`、`GET/POST /api/v1/password-reset-tickets` |

### 6.3 安全口径（逐条可查）

| 要求 | 实现 |
|---|---|
| 不可枚举账号 | 存在/不存在/无邮箱一律 200 + `accepted:true`；不存在账号**不建工单、不发信**（UGC048 断言 `COUNT=0`） |
| 码只存摘要 | `code_hash` 为 SHA-256(归一化码)，UGC048 断言 64 位且不含明文 10 位 |
| 码单次 + 时效 | `markConsumed` 带 `PENDING` 守卫与乐观锁；30 分钟过期；复用 → 401，状态落 `CONSUMED` |
| 不能成为绕过 MFA 的通道 | 确认成功**不签发会话**，只改密 + `revokeAllFor`，用户必须重新走登录/二次验证（UGC048 有专门用例） |
| 口令策略不降级 | 复用 `PasswordPolicy.check`，弱口令 → 400/P1001（**先比码再验策略**，避免用策略错误探测码是否有效） |
| 邮件轰炸 | 同一登录名已有未结束工单时不再发第二封 |
| 通道不可用不假装成功 | 无邮箱或网关抛异常 → 工单落 `DELIVERY_FAILED`（运营可见、引导走客服）；只有真正投递成功才是 `PENDING` |
| 客服通道要授权 | 请求只建 `AWAITING_OPERATOR` 工单；OPERATOR/ADMIN 批准时才生成码，且码只在批准回执出现一次、不再落库 |
| 生产不静默降级 | `SecurityStartupValidator`：`mail-mode != unconfigured` 但容器里仍是兜底实现 → **启动失败**；`application-prod.yaml` 现为 `unconfigured` |

### 6.4 实测抓到的一个真实缺陷（已修，留档）

首轮集成测试 3 例失败，全部是"确认时好码被判无效 → 401"。根因：**签发端对
`ABCDE-FGHIJ`（带分隔符的展示码）取摘要，确认端先把分隔符归一化再取摘要**，两端口径不一致，
任何码都不可能命中。修法：签发/客服批准统一 `sha256(normalizeCode(code))`，展示归展示、摘要归摘要。
这类"两端各自归一化"的错，单测不写端到端就抓不到——正是本次要求"真实修 + 验证"的意义。

### 6.5 邮件通道：真实 SMTP 实现（已闭合）

原状态是"只有端口 + 明确失败兜底"。收尾时确认本机 `~/.m2` 里 **Spring Boot 4.0.9 BOM 已管理
`org.eclipse.angus:jakarta.mail:2.0.5`**，因此直接接真实现，不自造协议：

| 项 | 实现 |
|---|---|
| 适配器 | `lumin-infrastructure/.../identity/mail/SmtpPasswordResetMailGateway`（SMTP 会话/MIME/AUTH 全交给 jakarta.mail，代码只拼凭据与正文） |
| 装配 | `PasswordResetMailConfig`：`mail-mode=smtp` 装真实网关，其余装兜底；`@ConditionalOnMissingBean` 仍可被部署侧覆盖 |
| 参数 | `lumin.auth.reset.mail.{host,port,username,password,from,starttls,ssl,timeout-seconds}`，全部支持 `LUMIN_AUTH_RESET_MAIL_*` 注入 |
| 启动门禁 | `SecurityStartupValidator`：模式只允许 `unconfigured/smtp`（拼错直接失败）；`smtp` 而仍是兜底实现 → 失败；SMTP 参数不全、发件地址非法、带口令不开加密、STARTTLS 与 SMTPS 同开 → 构造即失败 |
| 传输安全 | STARTTLS `required=true`（服务器不支持就失败，不静默降级明文）、`ssl.checkserveridentity=true`、连接/读/写超时 |
| 头注入 | 收件人先过严格正则再用 `InternetAddress(addr, true)` 校验；`victim@x.com\r\nBcc:…` 一律拒投 |
| 日志口径 | 只记 `result=sent/failed` 与异常类型；不记收件人、不记重置码 |

验证（全部真实协议，无 mock）：

| 用例 | 覆盖 |
|---|---|
| `SmtpPasswordResetMailGatewayTest`(5，自带最小 SMTP 收件端 `SmtpSink`) | 报文按 `Content-Transfer-Encoding` 解码后含 10 位码与时效说明、`To` 正确；头注入与非法地址拒投且一封信都不发；带口令不加密拒启动；缺主机/发件地址非法拒启动；端口无人监听 → `MailDeliveryUnavailableException` |
| `UGC050SmtpPasswordResetIntegrationTest`(2) | `mail-mode=smtp` + 真实网关起上下文（启动门禁放行）→ 注册带邮箱 → 请求重置 → **从 SMTP 收件端读报文解出码** → 码能改密（旧会话 401、旧口令 401、新口令 200、工单 `CONSUMED`、库内只有摘要） |

> 为什么不用 GreenMail：它基于 `javax.mail`，与主代码 `jakarta.mail 2.0.5` 同处测试类路径时
> `org.eclipse.angus.mail.handlers.text_plain` 会被 `javax.activation.DataContentHandler` 强转失败。
> 与其为测试降级主代码依赖版本，不如自带一个 80 行的最小收件端——测的是**我们发的报文**，
> 反而更贴近真实投递。

生产部署只剩填参数：`mail-mode=smtp` + host/port/from（+ 认证与 TLS），域名证书走 JVM 信任库。

## 八、审计快照字段白名单（审查 12 项）

### 8.1 为什么必须改

`AuditAppender.recordTransition` 此前把调用方传的 `Map` **原样**序列化进 `before/after` 并算摘要。
调用方今天传的是状态字段，明天传进 `password`/`token`/`secret` 也没人拦——审计表是全站最长的
留存数据，一旦写进敏感值就不可撤回。

### 8.2 落地结构

| 项 | 实现 |
|---|---|
| 纯函数 | `audit/service/AuditSnapshotSanitizer`（无 IO、无 Spring 依赖，可单测） |
| 白名单键 | `businessState/restrictionState/holdState/configState/publicationState/roleGrantState/accountState/mfaState/deliveryState/appealState` |
| 白名单外 | 一律丢弃并计 `_dropped` 计数（"被拦了几个字段"本身可审计，不静默） |
| 体量上限 | 最多 12 项、单值 120 字符（超长截断） |
| 空输入 | `null` / 空 Map / 全被拦且无计数 → 返回 `null`，不写 `{}` |
| 接线 | `AuditAppender.recordTransition` 先 `sanitize` 再序列化与算 digest |

> 口径说明：现有四处调用的键全部在白名单内，因此**历史 digest 不变**；白名单是"以后新增字段必须
> 显式登记"的闸门，而不是一次数据迁移。

验证：`AuditSnapshotSanitizerTest`(4)——白名单键保留、非白名单键丢弃并计数、超长截断与条数上限、
空输入返回 null。

## 十、仍未闭合（不要当成已解决）

1. **OIDC/PKCE**：本阶段是"自建账号 + BCrypt"，不是联邦身份。`user_profile` 已有
   `oidc_issuer/oidc_subject`，后续可平移到 OIDC（解析/撤销语义不变）。
2. **邮件通道已实现并验证**（§6.5），但**生产参数未填**：`lumin.auth.reset.mail-mode` 默认仍是
   `unconfigured`（兜底转客服）。上线只需配 `smtp` + host/port/from（+ 认证与 TLS），
   域名证书需在 JVM 信任库内；没有真实发信量的压测/退信处理（bounce）暂未覆盖。
3. **MFA 解绑是运营工单，不是自助**（§5）：需 OPERATOR/ADMIN 批准；若要做"用户自助 + 邮件确认"，
   需在解绑工单上再叠一次身份核验通道（可复用 §6 的码机制）。
4. **限流的分布面**：IP 配额（§3）与账号锁定（§1）都已闭环，但**分布式来源**（僵尸网络
   换 IP）仍需网关/WAF 侧口径；反向代理部署必须让网关重写 `remoteAddr`（不信任
   `X-Forwarded-For`，见 §3.3），否则配额会退化为"按代理 IP"。
5. **CORS 只在应用层**：`CorsPolicyConfig` 是应用内白名单，若前置 CDN/网关也加了 CORS 头，
   会出现两份不一致的 `Access-Control-Allow-Origin`；部署时**只保留一层**。
6. **审计白名单是"以后新增字段必须登记"的闸门**（§8），不是历史数据迁移：已写入的非白名单键
   不会被回溯清理（现有四处调用键本就在白名单内，实际无存量问题）。
7. **TOTP 库替换**：见 §2.3，能引依赖时应替换 `Totp.code/Totp.verify`。
8. ~~`docs/23` 内明文写着本地 root 口令~~ **已改占位符**（`<本地测试库账号/口令>`）。
9. **`release/*-debug.apk`**：上线前从发布物剔除；`allowBackup` 已改 `false`（见 §十二）。
