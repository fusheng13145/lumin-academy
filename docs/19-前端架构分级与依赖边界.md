# 19 · 前端架构分级与依赖边界

> 状态：已落地并纳入校验  
> 适用范围：`lumin-frontend` 的 Web 端与 Android（Capacitor）端  
> 结论：前端不照搬后端的 5 个物理 Maven 模块，采用「纵向 feature 切片 + 共享层 + 展示壳」的逻辑分级。

## 1. 为什么不做前端物理模块

后端拆 `domain/application/infrastructure/ai/bootstrap` 是为了编译期依赖、部署单元、DI 装配和领域不变量边界。前端当前是：

- 单个 Vite 构建；
- 单个 React 树；
- 单个 Capacitor APK；
- 单团队、单仓库、单发布节奏。

此时拆成多个 npm workspace 只会增加构建编排、路径别名、版本联动和 CI 成本，并不会带来真实的运行时隔离。前端需要的是**可检查的依赖方向**，不是更多 `package.json`。

## 2. 目标分层

```text
┌─────────────────────────────────────────────┐
│ app/            组合层：路由、Provider、启动编排    │
│                唯一允许组合所有 feature 的地方      │
├─────────────────────────────────────────────┤
│ mobile/         展示壳：Android 页面、导航、Capacitor │
│ features/       纵向切片：reader/author/studio/...  │
│                 每个切片内部再分 ui/model/api        │
├─────────────────────────────────────────────┤
│ components/     共享 UI                              │
│ services/       共享 API client / 适配器              │
│ types/          共享类型                              │
│ lib/            纯规则 / 轻量 domain（零 React）       │
│ mocks/          演示夹具                              │
│ styles/         design tokens / global / mobile       │
└─────────────────────────────────────────────┘
```

依赖方向固定为：

```text
app -> features / mobile / shared
mobile -> features / shared
features -> shared（只能同 feature 内部互相引用）
shared -> 不得反向依赖 features / mobile / app
```

### 各层职责

| 层 | 当前目录 | 职责 | 不应该做什么 |
|---|---|---|---|
| 组合层 | `src/app` | 工作空间切换、全局 Provider、启动装配 | 不放具体业务页面；不被共享层引用 |
| 展示壳 | `src/mobile` | Android 页面、移动路由、返回键、Splash、本地持久化编排 | 不反向依赖 `app`；不直接写后端 SQL/领域规则 |
| 功能切片 | `src/features` | 按读者/作者/审核/运营/账号纵向组织页面与交互 | 不跨 feature 读私有文件；不依赖展示壳 |
| 纯规则层 | `src/lib` | 三模式规则、工作空间配置等无 React 规则 | 不放 JSX、不调浏览器 API |
| 共享 UI | `src/components` | 可复用布局、图标、基础控件 | 不 import `app`，不 import 业务 feature |
| 共享服务 | `src/services` | HTTP、envelope、服务适配 | 不 import 页面/壳 |
| 共享类型 | `src/types` | 跨 feature 的稳定类型 | 不放运行时逻辑 |
| 演示数据 | `src/mocks` | 本地夹具 | 不反向依赖 UI |

## 3. 本次已落地的改造

### 3.1 三模式规则上收

新增 `src/lib/creationMode.ts`，作为 Web 与 Android 共用的唯一规则源：

- `CreationMode` 类型；
- `CREATION_MODES`、`MODE_LABEL`、`MODE_DESC`；
- `usesAi()`：传统模式不进入 AI 流程；
- `upgradeModeForInsert()`：传统模式插入 AI 候选后升级为辅助模式；
- `normalizeCreationMode()`：持久化值损坏时回退到传统模式。

`src/mobile/types.ts` 不再重复定义模式，改为从 `lib` 再导出；`aiDemo.ts`、`AiScreen.tsx`、`EditorScreen.tsx`、`MobileApp.tsx`、`navigation.ts` 均改为引用纯规则层。

### 3.2 移动端 model 拆分

`src/mobile/MobileApp.tsx` 由约 419 行降至约 237 行，只保留页面组合与渲染。新增：

| 文件 | 职责 |
|---|---|
| `src/mobile/model/drafts.ts` | 草稿默认设置与 `buildDraft()` 唯一构建入口 |
| `src/mobile/model/useMobileWorkspace.ts` | 阅读设置、进度、记忆、草稿、模式、主题的加载与持久化 |
| `src/mobile/model/useMobileNavigation.ts` | 移动路由、浏览器历史语义、Android 返回键、Tab 切换 |
| `src/mobile/model/useDraftWorkflow.ts` | 打开编辑器、保存、插入 AI 候选、提交审核 |

收益：屏幕组件不再直接操作 Capacitor 或 Preferences；草稿流程可被 Web 壳替换为真实 API 适配，而不改页面。

### 3.3 修正共享层反向依赖

原 `components/layout/BottomTab.tsx` 与 `TopNav.tsx` 直接 import `app/navigation`，形成 `shared -> app` 的反向边。已将工作空间配置下沉到 `src/lib/workspaces.ts`，`app/navigation.ts` 仅做再导出；共享布局改为引用 `lib`。

### 3.4 依赖边界自动校验

新增 `lumin-frontend/scripts/check-import-boundaries.mjs`，规则：

- `features/<a>` 不得 import `features/<b>`；
- `features` 不得 import `app` 或 `mobile`；
- `components/lib/mocks/services/styles/types` 不得 import `features`、`mobile`、`app`；
- `mobile` 不得 import `app`；
- 忽略第三方包与非相对路径。

接入命令：

```bash
npm run check:architecture   # 单独检查
npm run lint                 # eslint + 边界检查
npm run verify               # lint + test + Web build + Mobile build
```

当前结果：`前端依赖边界检查通过：61 个源码文件`。

## 4. 页面与模式的衔接

三种模式共用同一个编辑器外壳，但 AI 介入程度不同：

| 模式 | 编辑器行为 | AI 介入 | 内容归属 |
|---|---|---|---|
| 传统写作 | 纯文本编辑、自动保存、章节发布 | 不主动调用；作者可手工打开素材库 | 作者原创，平台仅按协议获得展示授权 |
| AI 辅助 | 作者选区/段落请求候选，候选以 diff/预览出现 | 单次 workflow，作者逐段采纳 | 作者主导；AI 候选未采纳前不进入正文 |
| 纯 AI 写作 | 作者只填方向、约束、章节目标；查看候选章节 | workflow + multi_agent，长期记忆驱动 | 候选默认 `ai_candidate`，作者确认后才成为章节 |

模式切换入口在编辑器底部与 AI 创作台；切换只改变“下一次生成”的策略，不重写已有正文。插入候选时若当前为传统模式，按 `upgradeModeForInsert()` 升级为辅助模式，避免“传统模式却出现 AI 正文”的口径矛盾。

## 5. 后续演进触发条件

当前**不做** `components/services/types/mocks/lib` 到 `shared/` 的物理大迁移，也不引入 npm workspaces。出现以下任一条件再升级：

1. Web 与 iOS 需要独立发布节奏；
2. 前端团队超过 3 人，跨 feature 合并冲突成为常态；
3. 单次 Vite 构建超过可接受阈值；
4. 同一 feature 需要被第二个应用复用；
5. 需要独立部署某个前端子应用。

届时按「先抽 `shared/`，再抽 feature 包，最后拆 workspace」的顺序渐进迁移，不做一次性目录重写。
